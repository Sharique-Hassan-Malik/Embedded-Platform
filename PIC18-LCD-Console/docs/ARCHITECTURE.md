# Architecture

## Overview

A single-chip arcade game console built around the PIC18F4550 microcontroller.
The firmware implements the complete Breakout game including a custom sprite and
text rendering layer, a KS0108 parallel LCD driver, debounced button input and
persistent high-score storage in the MCU's internal EEPROM.  No operating
system, no HAL and no game library are used anywhere.  The game loop runs at a
fixed 30 Hz tick generated by Timer0 overflow.

## Block Diagram

```
Timer0 ISR (30 Hz)
    │
    └── tick_flag = 1
             │
             ▼
     buttons_update()    ← samples PORTB, advances debounce counters
             │
     game_tick()         ← advances state machine one frame
             │
             ├── move_paddle()     ← reads btn_held(LEFT/RIGHT)
             ├── move_ball()       ← physics + wall / paddle / brick collisions
             │       └── check_bricks()   ← AABB per-brick collision
             ├── ADSR / dead timer logic
             └── eeprom_save_hiscore()    on new high score
             │
     game_render()       ← writes to lcd_fb[][]
             │
             ├── lcd_clear_fb()
             ├── render_status()   ← gfx_str / gfx_uint_pad
             ├── render_bricks()   ← gfx_fill_rect per alive brick
             └── render_entities() ← paddle and ball rectangles
             │
     lcd_flush()         ← transfers lcd_fb[8][128] to KS0108 via SPI parallel
```

## Module Descriptions

### `main.c` — System entry point

Initialises the oscillator at 8 MHz, configures Timer0 for a 30 Hz overflow
interrupt and starts the game loop.  The main loop is a tight spin-on-flag
pattern: the ISR sets `tick_flag` and the foreground reads it, keeping all
game logic and rendering synchronous with the hardware tick.

**Timer0 derivation:**
```
Fcy            = Fosc / 4 = 8 MHz / 4 = 2 MHz
Timer0 clock   = Fcy / prescaler = 2 MHz / 8 = 250 kHz
Counts/period  = 250 000 / 30 = 8 333
Reload value   = 65 536 – 8 333 = 57 203 = 0xDF53
```

The reload is written to TMR0H:TMR0L inside the ISR before clearing the flag
to cancel accumulated interrupt-entry jitter.

### `lcd.c` — KS0108 display driver

The KS0108 display contains two identical controller chips, each managing 64
columns.  CS1 selects the left half (columns 0–63) and CS2 selects the right
half (columns 64–127).  Each chip organises its 64×64 pixels into 8 pages of
8 rows; data is written one full byte (8 vertical pixels) per write.

The framebuffer `lcd_fb[8][128]` maps directly onto this structure.
`lcd_flush()` iterates over all 8 pages and writes 64 bytes to each half,
for a total of 1 024 data bytes per frame.  At 8 MHz with 2 µs per write
cycle, a full flush takes approximately 2 ms, comfortably within the 33 ms
frame budget.

Pin assignments:

| Signal | PIC18 pin | Direction |
|---|---|---|
| D0–D7 | PORTD | Output |
| RS | RE0 | Output |
| R/W | RE1 | Output (always 0) |
| E | RE2 | Output |
| CS1 | RC0 | Output |
| CS2 | RC1 | Output |

### `gfx.c` — Drawing primitives

All drawing targets the framebuffer and uses `gfx_pixel()` as the single
write primitive.  Clipping is applied at the pixel level.

The framebuffer bit layout: `lcd_fb[page][col]`, where `page = y / 8` and
`bit = y % 8`.  Bit 0 is the top pixel of the page; bit 7 is the bottom.

`gfx_char()` renders a 5×7 glyph by iterating over the 5 column bytes of
`font5x7[]` and drawing each set bit.

### `font.c` — 5×7 bitmap font

64-entry table covering ASCII 0x20–0x5F (space through underscore), stored in
flash.  Each glyph is 5 bytes; byte N is the bitmap for column N of the
character with bit 0 at the top row.

### `buttons.c` — Debounce engine

Reads PORTB once per 30 Hz tick.  A state change is accepted only after
`DEBOUNCE_COUNT` (3) consecutive identical samples, giving 100 ms hysteresis.
`btn_pressed()` returns a single-fire edge flag that clears itself on read,
suitable for detecting menu selection without key-repeat.

### `eeprom.c` — EEPROM persistence

Uses the PIC18 hardware EEPROM interface (EEADR / EEDATA / EECON1/2).  The
mandatory unlock sequence (0x55 / 0xAA writes to EECON2) is performed with
interrupts disabled to prevent corruption.  A magic byte at address 0x00
distinguishes a freshly erased device from an initialised one.

### `game.c` — Breakout engine

**State machine:**

```
GS_TITLE ──FIRE──► GS_LAUNCH ──FIRE──► GS_PLAYING
                                            │
                               brick hit or wall ───── continue
                                            │
                                     ball off bottom
                                            │
                                       GS_DEAD (30-frame timer)
                                            │
                                  lives>0 ? GS_LAUNCH : GS_GAME_OVER
                                            │
                                     GS_GAME_OVER ──FIRE──► GS_LAUNCH
                               bricks_left==0
                                            │
                                       GS_LEVEL_UP (45-frame timer)
                                            │
                                   level++, reset_bricks(), GS_LAUNCH
```

**Ball physics:**

The ball moves by `(ball_dx, ball_dy)` pixels each frame.  Reflection is
performed by negating the appropriate velocity component:

- Side walls: negate `ball_dx`
- Top wall (below status bar): negate `ball_dy`
- Paddle: negate `ball_dy`; left third of paddle forces `ball_dx` negative,
  right third forces positive, centre preserves current angle

**Brick collision (AABB):**

For each alive brick, the axis of minimum penetration depth determines which
velocity component is negated:

```
ox = min(ball_x+BALL_SIZE - bx,  bx+BRICK_W - ball_x)   x-axis overlap
oy = min(ball_y+BALL_SIZE - by,  by+BRICK_H - ball_y)   y-axis overlap

if oy <= ox:  vertical approach  → negate ball_dy
else:         horizontal approach → negate ball_dx
```

Only one brick is destroyed per frame to prevent a double-flip from two
simultaneous collisions.

**Level progression:**

Clearing all 40 bricks increments `level` and resets the grid.  Ball speed
increases by 1 pixel/frame each level up to level 3 (`BALL_SPEED = 3`).
Score per brick equals `level × 10`.

## Hardware Schematic Notes

```
PIC18F4550                         KS0108 128×64 LCD module
─────────────────                  ────────────────────────
RD0–RD7  ──────────────────────►  DB0–DB7   (data bus)
RE0      ──────────────────────►  RS        (0=cmd, 1=data)
RE1      ──── GND ─────────────►  R/W       (always write)
RE2      ──────────────────────►  E         (enable strobe)
RC0      ──────────────────────►  CS1       (left half)
RC1      ──────────────────────►  CS2       (right half)
VDD      ── 10 kΩ ──────────►  RST tied to VDD via RC  (power-on reset)

Buttons (active low, 10 kΩ pull-ups to VDD):
RB0 ── BTN_LEFT
RB1 ── BTN_RIGHT
RB2 ── BTN_FIRE

Power: 3.3 V or 5 V (KS0108 modules are typically 5 V; check module datasheet)
LCD contrast pot: 10 kΩ trim pot between VDD and GND, wiper to V0 pin
```

## Resource Usage

| Resource | Usage |
|---|---|
| Flash | ≈ 6 KB code + 320 B font table |
| RAM | 1 024 B framebuffer + ≈ 80 B game state + stack |
| EEPROM | 3 bytes (magic + 2-byte high score) |
| Timer0 | 30 Hz game tick |
| PORTD | LCD data bus |
| PORTE (3 pins) | LCD control |
| PORTC (2 pins) | LCD chip selects |
| PORTB (3 pins) | Button inputs |

## Building

1. Open MPLAB X, create a new project for PIC18F4550.
2. Select XC8 as the toolchain.
3. Add all `.c` files in `firmware/` to Source Files.
4. Add all `.h` files to Header Files.
5. Set `_XTAL_FREQ = 8000000` in project properties (or rely on the
   `#define` in `main.c`).
6. Optimisation: `-O1` or higher.
7. Program with PICkit 3/4 or SNAP.
